# Decisions

Working notes on judgment calls made while finishing the open items, so a reader can see what was decided and why.

## The checklist

- **No TODO.md exists** in the working tree, on this branch, on `main`, or in any other branch of the repository, and nothing refers to one. The only checklist with open boxes is `docs/ROADMAP.md`, which is the project's own to-do list. Its unchecked items were taken as the TODO list and are checked off there as each is finished: the classic-menu verification (M0), the openly licensed test corpus (M0), on-device generation (M7), and DICOM and FITS tools (M8).

## Order of work

1. **DICOM and FITS tools** first: the best-defined item, building on readers finished in the previous chunks.
2. **Test corpus**: a fetch script with a license manifest rather than files committed to the repository (see below).
3. **Classic menu verification**: against the programs' published documentation, since installed copies are not available here (see below).
4. **On-device generation** last: the largest item, with the model choice constrained by the project's license rule.

## Test corpus

- **Not committed.** Real camera files are 1–40 MB each; the corpus (376 MB) is fetched by `scripts/fetch-corpus.py` into `tests/corpus` (ignored by git) with a manifest of URL, license, size and SHA-256. The repository keeps the small generated fixtures.
- **CC0 only from raw.pixls.us.** The site also carries CC-BY-NC-SA samples; they are skipped, since the project should not take on attribution or non-commercial terms for test data. Every download is checked against the site's SHA-256.
- **NASA FITS samples** are public domain as US government works. No other external sources were added: the project's own generators already cover the other formats with files it owns.
- **Damaged files are made, not collected.** Cutting, zeroing and flipping the downloaded files gives reproducible damage for the recovery engine; the test accepts either a decoded picture or a plain error, never a hang or a crash.
- **One gap the corpus found was fixed** rather than listed: Kodak DCR/KDC, Epson ERF, Hasselblad 3FR/FFF and Phase One IIQ files carry no JPEG preview, only an uncompressed TIFF thumbnail, which the RAW preview path now shows. Minolta MRW has neither; it now develops (see RAW families below).
- **LibRaw as the reference, not as code.** `scripts/fetch-corpus.py --refs` writes LibRaw's reading of each sample (through rawpy, on the developer's machine) so the app's own readers can be compared sample by sample; nothing of LibRaw enters the app.

## Classic menu verification

- **Documentation instead of installed copies.** No Windows or macOS programs can be installed here, so each layout was checked against the program's own published menu definitions and shortcut lists: IrfanView's official English-GB menu resource and hotkeys page, XnView MP 1.12.2's menu bars (author's statement and dated screenshots for the item lists), FastStone 8.5's menu definitions and help file, ACDSee Photo Studio Ultimate 2026's help, Picasa 3.9's own string tables and Google's shortcut list, Apple's Preview User Guide, the digiKam 8.8 manual. The research notes stayed outside the repository; this file records the outcome.
- **Where documentation was incomplete, the plan was left alone**: ACDSee's menu order is not documented (only membership), Preview's Window and Help menus are not described by Apple, and Microsoft no longer documents Windows Photo Viewer at all; the Windows Photo Viewer layout therefore stays as planned.
- **Menu arrangement**: seven layouts were rearranged to the documented menu bars: IrfanView (border/canvas size and Show Channel under Image, lossless JPEG and e-mail under Options, multipage navigation under View as in the program), XnView MP (a Metadata menu, no Window menu, Settings under Tools), FastStone (the Settings menu, lossless rotation under Tools, Red-Eye and JPEG Comment under Edit, border and watermark under Effects), ACDSee (a Panes menu; Modify, Zoom, Batch and Create as Tools submenus), Picasa 3 (the File, View, Folder, Picture, Create and Tools menus follow the program's string tables), Preview (New from Clipboard, Duplicate and Revert in File; Two Pages and Soft Proof in View; the Annotate submenu in Tools) and digiKam (Browse and Edit menus added; Import and Export after Tools; the editor's adjustments under Tools ▸ Image Editor). Anne's Lens commands the programs lack keep a sensible place in each layout rather than being dropped.
- **Default keys**: nine corrections from the documentation: Email Shift+M and Comment Ctrl+Shift+M (IrfanView; the plan had them crossed), Auto Crop Borders Ctrl+Shift+Y (IrfanView; Shift+X is XnView's Crop), Lossless Crop Ctrl+Shift+J (IrfanView), Random Picture Ctrl+M (IrfanView), Lossless Auto-Rotate by EXIF Ctrl+Alt+A (FastStone), People Ctrl+F6 (ACDSee). Two Anne's Lens keys moved out of the way: Go to Picture Number to Ctrl+J and Compare Pictures to Ctrl+Alt+Y (FastStone's P and XnView's Shift+C both collide with IrfanView keys the plan keeps).
- **Not adopted**: single-letter and Alt+letter defaults of other programs that would collide with IrfanView's letter keys or with menu mnemonics, and full-screen-only keys.

## On-device generation

- **Transformers.js rather than a hand-written pipeline.** Janus generates a picture as 576 image tokens from a 1.3-billion-parameter language model with classifier-free guidance, then decodes them; Transformers.js (Apache-2.0) implements that loop, the tokenizer and the chat template for the ONNX export. Driving ONNX Runtime directly would mean re-implementing all of it blind, without a GPU here. The runtime loads on demand like the others (the build's own copy for the desktop's strict Content Security Policy, the pinned CDN otherwise); its bundled ONNX Runtime files travel with it, since its version differs from the app's.
- **The model.** No text-to-image model exists today that is both permissively licensed and small enough for a browser (checked: Sana, Kandinsky, Würstchen, Infinity, OmniGen, Show-o are Apache-2.0 or MIT but need 2–8 GB and have no browser pipeline; SDXS, aMUSEd and the Stable Diffusion family carry OpenRAIL licenses). Janus-Pro-1B is the only one with a browser pipeline and a feasible size. The hub tags its ONNX export "MIT", which is the code license; the weights are under the DeepSeek Model License (commercial use allowed, use restrictions in its Attachment A). The project's rule for on-device models is permissive licenses only, so: the model is never bundled or fetched without an explicit choice, the download dialog names the license as it is and asks for acceptance, the documentation says so, and the default is swapped the day a permissive model of browser size appears. This is the one place the project departs from its rule, and it is recorded here for the maintainer to confirm or reverse.
- **Scope.** Prompt to picture only (384 × 384, up to four at once); edits, masks, variations and references stay with the picture services, as the model has no such inputs. Phones get the service with a warning rather than nothing (AI-PLAN.md planned desktop-only); the warning says what to expect.
- **Verification.** The plumbing (service, wizard, download dialog, generation, provenance, history) is covered by unit tests with a fake generator and the e2e test; `scripts/try-device-generation.mjs` runs the real model in Node against the same Transformers.js API so the integration can be checked end to end, which was done once here on the CPU.

## DICOM and FITS tools

- Four commands rather than a tool palette: Window / Level, DICOM Tags, FITS Stretch, FITS Header. They sit in the Image tab ("Scientific pictures") and the IrfanView-style Image menu; ids carry the tab's prefix as every command does.
- Display settings are **per file, in memory** (`decodeOptions.perEntry`), and the file is decoded again with them. They are not written to the file or saved across runs: a DICOM or FITS file's own values must stay what they were, and Save As writes the picture as shown, which is the usual way to keep a view.
- The CT presets are the common radiology values (brain 40/80, lung −600/1500, bone 400/1800 …); they are offered on every DICOM file, since the modality is not always filled in.
- The logarithmic and asinh stretches use SAOImage DS9's formulas (log₁₀(1 + 1000 t) / 3, asinh(10 t) / asinh(10)) so astronomers get the curves they know.
- The tag dump keeps every sequence's items (the reader normally keeps only the ones it uses) through a module flag set for the dump alone; the dictionary covers the modules pictures carry, not all of PS3.6, and names private tags "private".
- The dialogs accept arguments (`{ wc, ww, fn }`, `'full'`, `'file'`; `{ mode, percentiles | lo, hi }`, `'default'`) so scripts, macros and the tests can apply settings without the dialog.

## The second round of leftovers

The first round checked every box that existed and left four roadmap lines open; this round added explicit boxes for the real gaps the finished work had noted and implemented them.

- **WCS: CSC, HPX and XPH.** Ported from the WCS papers and wcslib's `prj.c`: the COBE quadrilateralized spherical cube with its 28 single-precision polynomial coefficients (hence a 0.02″ tolerance against astropy, which also computes in single precision there), HEALPix with its facet offsets and polar logic, and the butterfly projection. Fixtures from astropy as for the other projections; every projection of the papers is now covered.
- **Merge refinements** are built on the stitcher's feature machinery rather than a second alignment: a similarity transform (shift, turn, scale) is enough for hand-held brackets, and perspective would let a bad match warp a picture badly. Ghost removal follows the usual weight approach (Mertens/Kautz lineage): the exposure closest to the median exposure is the reference, every other exposure is gained to it, and its weight falls off with the luminance difference, so a moving person is taken from the reference alone. Clipping is judged before the gain, or a bright object in the dark exposure would pass as clipped and slip through (the test caught exactly that).
- **Atari ST color cycling** plays as an animation: Degas Elite's footer channels and NEOchrome's animation words give the color range, direction and speed; the frames are the palette's turns at 60 Hz VBL timing. Spectrum 512's compressed .spc and the Tiny and Crack Art packers stay listed as not done.

## RAW families

- **Own code, no module.** The roadmap planned an optional LibRaw module because the mature decoders are LGPL/CDDL. The families were read directly instead: the formats are documented TIFF variants plus a handful of codings (Nikon's Huffman, Sony's ARW2, Panasonic's version 4, Kodak's 65000, Canon's sliced lossless JPEG), each a page of code once the structure is known. No module download, no LGPL text in the app, and the DNG developer serves every family. LibRaw is used only on the developer's machine, as the reference the test corpus is compared with (identical sensor values on all 23 supported samples).
- **Scope by evidence.** Every reader was written against a real file from raw.pixls.us (CC0) and compared with LibRaw before being counted; families without a sample or with a large proprietary codec are refused with a stated reason rather than guessed at: CR3 (CRX), CRW (Canon's older Huffman tables), X3F (Foveon), IIQ, 3FR/FFF, SRF (encryption), Kodak DC120's KDC (a camera-specific layout), Mamiya MEF (no sample), X-Trans RAF, 14-bit RW2 (versions 5–7), Canon sRAW. The Huffman NEF trees are dcraw's documented tables; the 12-bit lossy tree is verified by the D2H sample, the other four trees are the same table but have no sample here.
- **Color without matrices.** These files carry no camera color matrices (LibRaw ships Adobe's table of them; copying it would bring its license and 1000 cameras of upkeep). The developer treats the sensor's channels as sRGB primaries: neutrals, exposure and tone are right, saturated colors come out somewhat flat. The documentation says so, and a DNG conversion of the same file gives the camera's own colors through the same developer. White balance is read from the maker data where it exists (Nikon, Pentax, Olympus, Epson, Canon, Sony's decrypted SR2 block, Leaf, Fujifilm, Minolta, Panasonic); gray-world otherwise (Samsung).
- **Black and white levels** come from the file where it states them (Sony, Pentax, Olympus, Fujifilm, Panasonic with LibRaw's +15, Nikon's 0x3d) or from Canon's masked columns (the median left of the active area, 257 against LibRaw's 256). Where neither exists the level is 0 and the white is the bit depth's; LibRaw's camera table knows better for a few (Nikon P330's 200, Minolta's 3965, Samsung's 15872), a known, small difference the corpus test allows.
- **Crops** use the camera's own figures (Canon's SensorInfo borders, Panasonic's crop tags, Fujifilm's output size) rather than LibRaw's table of margins, so they can differ from LibRaw's by a few pixels; the sensor data is kept whole and compared whole.
- **Unverified in CI**: Panasonic's bit reader and the Nikon Huffman decoder have no synthetic fixtures (an encoder would be as intricate as the decoder); they are verified by the corpus test, which runs when the corpus is fetched. Everything else has small files written in the unit tests.

## Network sharing and shared albums

- **One server, two kinds of room.** The desktop's Phone Remote already ran a token-protected HTTP server; sharing got its own module (`electron/netshare.cjs`) on the same pattern rather than a second mechanism: a view room publishes the host's picture, zoom and pan as JSON plus a JPEG rendition, an album room publishes a listing with thumbnails and serves the files. Only requests carrying the 128-bit token are answered, and the server stops with the last share.
- **The suite's relay exists now as a script in this repository** (`scripts/relay.mjs`, about a hundred lines, in memory only), speaking the same protocol, so the web app can share at all and guests beyond the local network can follow. Anne's Stage planned a WebRTC signaling relay; a plain HTTP relay with server-sent events was chosen here because the data is small, one-directional and tolerant of latency, and because it needs no STUN/TURN infrastructure. Files are never relayed (size and privacy); the relay carries thumbnails for albums.
- **Renditions, not files, for shared views**: what the host shows (long side 1600 px, JPEG) travels, not the original, which may be a 60 MB RAW; a guest who has the same file open gets it at full quality from their own copy (matched by name and size). The rendition is also what makes a plain browser a guest.
- **Guests in the desktop app and on Android poll** the room (conditionally, every 400 ms) through the native layer instead of using the event stream: the desktop's content security policy limits the page to https and localhost, and Android's web view refuses mixed content; the native layer has no such limits. Browsers use the event stream.
- **Uploads are files only**: an added picture is written into a folder the host chose in the system dialog (so the app has write permission there), under a name made safe and never overwriting, capped at 64 MB; the host's album gains it and the host is told.
- **No accounts, no discovery.** Sharing is a token address shown as a QR code and copied as text; whoever holds the address is a guest. That matches the Phone Remote and keeps the feature usable without any sign-in.

## The two boxes left open

- **8BF plug-in host (Windows)**: not built. A host for Photoshop filter plug-ins must load Windows DLLs (most are 32-bit) and implement the plug-in API's callbacks in a native helper process; that needs a Windows build and test machine and sample plug-ins, none of which this environment has (no Wine, no MinGW). The planned `fx.plugins8bf` command stays unregistered, as the project's rule for unfinished commands requires. The box stays open rather than being checked off as a decision.
- **HEIC module**: the design is settled (libheif with libde265 through the `libheif-js` package, LGPL-3.0, loaded on demand like the other decoder runtimes, with its license and the HEVC patent notice shown first, as LEGAL.md describes) but the dependency could not be installed in this session: the package installation was refused by the session's safety policy, and the project's rule is not to work around such a refusal. The fixture path is ready (pillow-heif encodes test files from drawn pictures); the box stays open for a session where the install is allowed.

## DICOM blending

- Blending softcopy presentation states (PS3.3 A.33.5) are read like the other states: the underlying picture is the one the state opens, the superimposed one is found among the folder's files by SOP instance UID, decoded with the window the state gives it, mapped through the state's palette and composited at its relative opacity (a float, read as one). Spatial registration between the two is not applied: the superimposed picture is scaled to the underlying one, which is right when both share a frame of reference and approximate otherwise; the note on the picture says what was done.
